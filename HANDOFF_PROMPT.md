## What's been built/fixed this session, in order

1. **Dynamic input capability** (`core/pe_feature_extractor.py`) — real PE binary (.exe/.dll) upload support using `pefile`. Header+Entropy extracted exactly; API+Network extracted via hash-bucket approximation of real imports/strings (disclosed as approximate, not exact reconstruction of the original training encoding).

2. **Out-of-distribution safeguard** (`data/ood_node_thresholds.json`, `core/pe_feature_extractor.py:check_node_ood`) — real 99th-percentile thresholds computed from actual training data, not guessed. Flags a node's values as unreliable if statistically implausible vs. real training samples; such nodes get treated as honestly unfilled.

3. **Real-world generalization gap found and measured** (not assumed): tested the GNN pathway against 138,047 real independent PE samples (Kaggle `amauricio/pe-files-malwares` dataset, `kaggle_dataset/data.csv`, pipe-delimited, schema auto-detected via `core/graph_constructor.py:is_amauricio_schema`) and PAC-X against 43,876 real dynamic Cuckoo Sandbox API-sequence traces (`kaggle_dataset/dynamic_api_call_sequence_per_malware_100_0_306.csv`). Found: GNN had an **89% false-positive rate** on real independent benign software; PAC-X had a **95.9% false-negative rate** on real malware behavior. The paper's 99%+ numbers are real but describe in-distribution performance, not generalization — this was the honest finding that justified the next two fixes.

4. **GNN benign-robustness fix** (`scripts/train_with_kaggle_augmentation.py`, `scripts/validate_augmented_model.py`) — fine-tuned on the original training set + 20,000 real benign Kaggle samples (Header+Entropy real, API+Network honestly zero, matching what live uploads actually look like). Result, real and validated on a disjoint holdout: **89.0% → 0.02% false-positive rate**, in-distribution accuracy barely moved (99.61% → 99.51%). **Promoted to the live `model.pt`** (original backed up at `model.pt.pre_augmentation_backup`). Real disclosed trade-off: this specific header-only input shape now has a ~100% false-negative rate for malware (proven, not assumed) — **two separate attempts to fix this by adding malicious samples to the retrain pool both caused catastrophic training collapse** (accuracy crashing to 84.65%, then 63.27%) because data.csv has no malware family labels and pseudo-labeling them randomly created an unlearnable, self-contradictory target. Do not repeat that approach with a different dataset without a real family-labeled source.

5. **PAC-X evidence-weighted scoring** (`scripts/mine_pacx_api_signals.py`, `core/pacx_analyzer.py`) — replaced a small hand-picked 10-API keyword list (including one, `ConnectNetwork`, that wasn't even a real Windows API) with log-likelihood-ratio weights mined from the real Cuckoo Sandbox data (proper 60/20/20 train/val/test split, threshold chosen by *balanced* accuracy since the source data is 97.5% malware / 2.5% benign — raw accuracy would be misleading). Result: **49.8% → 80.6% balanced accuracy** on a genuinely held-out test split. One real regression found and fixed: applying the same dynamic-trace weights to *static* import-table content (raw binary uploads) caused a false positive on real notepad.exe — fixed with a `min_weight=2.5` damping specifically for `input_type == "pe_binary"`, since static linkage is weaker evidence than dynamic execution. **This damping value is a reasonable-but-unvalidated guess, not evidence-based** — see the open item below.

9. **Confidence calibration investigated, found not to help** (`scripts/calibrate_confidence.py`) — properly fit a temperature-scaling factor (T=7.25, minimizing NLL on real mixed in-distribution + external Kaggle data, proper disjoint calibration/report split). Mathematically safe (temperature scaling can't change argmax, so accuracy is provably unaffected) but **doesn't solve the underlying problem**: at the fitted T, 99.99% of everything falls below the 60% Agent-2 threshold, not selectively the wrong predictions — because confidence for correct and incorrect header-only predictions is statistically indistinguishable (both ~100.0%, verified with a real correct-vs-wrong confidence sweep). This is a **representational limit**, not a calibration bug: with only 2 of 4 signal channels, the model's logits don't encode "I don't know" as distinct from "I'm sure it's benign." **Not deployed** — don't try to wire this in without solving the underlying representation problem first.

10. **Agent 2's 60% threshold investigated** — confirmed it's an untuned round-number design constant in the paper (no derivation given anywhere). Important mechanical fact: the fusion `confidence` field is constructed as "confidence in whichever label won," so it's mathematically always ≥ 0.5 — **lowering** the threshold shrinks the trigger band (0.50 would make it literally impossible to ever fire), **raising** it widens it. This is the opposite of what "reduce the threshold" intuitively suggests. A real threshold sweep (0.50 to 0.99) on real header-only holdout data found **no threshold value meaningfully separates correct from incorrect predictions** there — same representational-limit root cause as item 9. However, the threshold **does work as designed** on the scenario it was actually built for: the leave-one-family-out zero-day experiment (already run in the prior session), where Emotet's holdout samples showed real, varying confidence and 31.58% correctly triggered Agent 2. Bottom line discussed with the user: **the core "zero-day from API logs" mission is genuinely backed by real experiments** (leave-one-family-out zero-day results, real PAC-X validation on real behavioral data) — the header-only/data.csv exploration was a valuable but *tangential* thread (that data has no API logs in it at all, just PE header numbers), worth being precise about which claims which evidence supports.
