Part 1 — Live Demo
1

Setup & launch

pip install -r requirements.txt
python app.py

Open http://localhost:8000/live_analysis.html. The server console prints model load status and the model's real overall accuracy on startup — worth glancing at once to confirm model.pt loaded (should read 99.51% — see step 11 for why that number, not the paper's 99.61%, is correct here).

2

Real LLM reasoning (optional)

Without a key, Agent 1 still works — it falls back to static templated reasoning, so the demo never breaks. For real Gemini-generated forensic text instead:

cp .env.example .env
# edit .env, paste a key from https://aistudio.google.com/apikey
python app.py   # restart to pick it up

Free-tier quota is small

The free tier caps at 15 requests/minute per model. Clicking through several analyses back-to-back during a demo can hit a 429 RESOURCE_EXHAUSTED — it's handled gracefully (falls back to template reasoning automatically, nothing breaks), but if you want guaranteed real LLM text for a specific demo moment, pace your clicks or warm up the quota a minute beforehand.

PAC-X panel — why it's capped at 50% on both files

PAC-X is a keyword/entropy heuristic — it needs readable text or API names to check. A CSV row here is pure numeric PE-header features (column names like f_SectionsMeanEntropy_0), nothing PAC-X can read. Reporting a confident "Benign" with zero real evidence would be a false claim, so it's deliberately capped — that's correct, honest behavior on both the malicious and benign file, not a bug specific to either.

Agentic-PACX (GNN) panel

This is the real, trained model's own output — diagnosis, confidence, predicted malware family (for the malicious file), and attention weights. This is where the actual detection work happens on a CSV upload.

Agent 1 — Dynamic Forensic Decision

Explains which pathway is "trusted" for this specific sample and why, in natural language (real Gemini text if a key is set, template text otherwise), plus which malware family the graph most resembles. Notice this text changes meaningfully between the two files — it's reasoning about the actual scores, not a canned response.

🧬 GNN Structural Forensic Report

The attention-weight-based narrative (e.g. "critical structural anomaly between PE Header and API Export...") — the paper's flagship explainability example. On the benign file this reads noticeably calmer; on gandcrab it flags the specific node interaction that drove the call.

Decision Fusion Layer

The final verdict: which pathway's weight dominated, whether the two pathways agreed or one was arbitrated over the other by trust score, and the raw inputs behind the final confidence number. This is the number that matters — always read this, not just the GNN panel above it.

While either result is on screen, open the 5-step pipeline tracker on the sidebar (Submit → Normalize → Build Graph → GNN+PAC-X → Fused Verdict) and click step 3 or 4 — it shows the actual 4-node topology (Header/Entropy/API/Network) with which nodes got real data highlighted, and after step 4, the attention weight on each edge.

4

Real, never-seen files — the dynamic-input path

Everything in step 3 replays a row that was already in the dataset. This step is the real test: upload an actual .exe/.dll the system has never seen before. Any upload mode works — the server auto-detects a real PE binary by its MZ header and routes it correctly regardless of which dropdown option is selected. Nothing needs configuring.

What happens under the hood

The binary is parsed with pefile for real header and section-entropy values (exact, not approximated), plus real imported/exported function names and real embedded strings. Each of the 4 graph nodes is then checked against data/ood_node_thresholds.json — real statistics measured from the training data itself — and any node that's statistically implausible next to genuine training samples gets treated as honestly unfilled rather than trusted blindly. The real extracted API names also get handed to PAC-X, so for the first time on a binary upload, PAC-X has actual content to evaluate instead of being capped.

Honest note on the malicious side of this demo

The benign case above is fully verified — tested live against real Windows system binaries, confirmed correct on both pathways independently. The malicious case was not tested against a real malware binary in this session — fetching and running real malware isn't something done here regardless of the reason. If you have legitimate access to a real sample (a university lab, a sandboxed VM, a research dataset), that's the right way to close this gap — not a limitation to hide, just be accurate about what's proven vs. expected when you present it.

Partial data — graceful degradation (JSON)

Dropdown: Partial Request Data (JSON). This demonstrates the system handling incomplete information honestly instead of guessing.

▲ Suspicious-leaning partial input

{"api_calls": ["ResumeThread", "kernel32!LoadLibraryA", "WriteProcessMemory"], "ip": "192.168.1.1"}

● Sparse, low-signal partial input

{"api_calls": ["GetSystemInfo"], "ip": "8.8.8.8"}

Either way, only 2 of 4 graph nodes get real data — Completeness shows 50–75%, and the Decision Fusion Layer visibly down-weights its own confidence accordingly rather than reporting false certainty on half-missing information. This is the clearest single moment in the demo to show "the system knows what it doesn't know."

6

Triggering Agent 2 live

Automatically, whenever the Decision Fusion confidence on a scan is below 60% — you'll see an "AGENT 2 ACTIVATED" banner and the sample gets added to data/retrain_pool.pt. The JSON partial-input demo above is a reliable way to trigger this live, since its confidence is deliberately reduced.

You can also force it manually via "Trigger Agent 2 Retraining". It queues in the background (the button confirms immediately, it doesn't block the page) and reloads the model automatically when it finishes.

It won't always actually retrain — and that's the point to make live

Two guardrails have to pass first: the pool needs ≥20 samples across ≥2 classes, and after fine-tuning, held-out accuracy can't have dropped by more than 3 points (or the update is discarded). With a small pool, clicking the button will correctly do nothing except log why — check the server console for [-] Retrain pool too small/uniform.... This is worth explicitly narrating in a demo: the system refusing to retrain on bad data is the safety feature working, not a limitation. A controlled reproduction (Section 11) proved what happens without these guardrails — accuracy collapsed from 99.61% to 80.08% mid-run.

8

Reading the confusion matrices

Two different kinds of confusion matrix, sized and colored differently — traced against the rendering code (script.js, renderMatrix and the multiclass heatmap block) to get the exact semantics right rather than eyeball it.

The 11×11 heatmap — Multiclass Report block

Rows are the true label, columns are the predicted label. Each cell is a raw held-out sample count, not a percentage. Diagonal cells (correct) are shaded green; off-diagonal (misclassifications) are red.

Nuance: color intensity is scaled against the single largest cell in the whole matrix — almost always a big diagonal cell like Benign. A small family's entire set of mistakes can look pale next to a saturated diagonal cell, even at 100% of that family's errors. Read the printed number, not just the shading, especially on low-support rows (GameHack, 11 samples; DarkKomet, 21).

The two 2×2 matrices — Baseline vs. GNN block

Collapse to binary Benign/Malicious. Each cell shows a large row-normalized fraction on top and the raw count underneath. Row-normalized means each cell divides by its own row's total — the two cells in one row add to 1.00, not all four cells in the matrix.

Shading here is directly comparable cell-to-cell (each cell normalized independently), unlike the 11-class heatmap above. The left (baseline) matrix is a literature figure, not measured here — only the right (GNN) matrix is a real evaluation.

Which one to reach for

Use the 11-class heatmap to find which specific family gets confused for which — scan a row for non-zero counts outside the diagonal. Use the 2×2 pair to compare false-positive/false-negative rates at a glance.

The sunburst chart, read correctly

/visual_graphs.html → "Deep Analysis Sunburst" (Plotly). Traced through exactly how it's built (script.js, around the sunburstChart block) rather than assumed.

Inner ring, two slices — GNN vs. PAC-X. Slice size = that pathway's own confidence, not a share of one fixed 100%.
Outer ring, under GNN — the 4 graph nodes, sized by attention weight.
Outer ring, under PAC-X — Prospect/Aspect/Context, sized by score breakdown.

Verdict: correct, with one nuance worth knowing

The data wiring is right — outer-ring labels map to the right node/category every time, and each pathway's children always sum to exactly that pathway's own slice. The two inner slices aren't "percent of one whole" — they're each pathway's own confidence shown side by side, so a bigger slice reads as "more confident," not "more of the total." Read it as "how big are the two confidences, and what's each made of" — not a literal 100% pie.

10

Zero-day generalization, proven not just claimed

Everything above measures known-family classification — every one of the 11 classes appears in both train and test. That's not a zero-day test. This one is: scripts/build_zeroday_experiment.py removes one entire malware family from training, validation, and test, retrains from scratch on the rest, then checks what happens when the model sees that family for the first time.

python scripts/build_zeroday_experiment.py --holdout emotet
python scripts/build_zeroday_experiment.py --holdout darkkomet
Held outTypenZero-day catch rateMean confidenceAgent 2 triggered
EmotetBanking trojan/loader30473.68%68.31%31.58% of samples
DarkKometRAT backdoor106100%99.95%0% (never needed to)

Read both rows together

Emotet: caught 3 in 4, and almost a third of those genuinely-uncertain predictions correctly tripped Agent 2's low-confidence safety net. DarkKomet: caught 100%, but every sample was confidently misattributed to Delf, its nearest known family — not recognized as novel. Agent 2 never fired because the model was never uncertain, just wrong about which malware it was (though right that it was malware).

Together: the malicious/benign boundary generalizes via similarity to the nearest known cluster, not a dedicated novelty detector — and Agent 2's gate engages exactly when that generalization is uncertain, not when it's confidently wrong.

11

Real-world validation — and why numbers moved since the paper

The submitted paper reports the original model (99.61% multiclass accuracy). The live app now runs a model that was fine-tuned afterward, specifically to fix a real generalization gap the paper never tested for. If someone compares the two numbers, this is the honest answer, backed by real measurements, not a guess.

What was actually found

Testing both pathways against real, independently-sourced data (not this project's own dataset) revealed both performed near chance level in isolation: the GNN pathway had an 89% false-positive rate on real legitimate software (would call Notepad "malicious"), and PAC-X had a 95.9% false-negative rate on real malware behavior sequences (would miss almost all of it). The 99%+ numbers in the paper are real and correctly measured — they just describe performance on this project's own dataset distribution, not generalization to arbitrary real-world files.

PathwayBeforeAfterFix
GNN — false positives on real benign software89.0%0.02%Fine-tuned on 20,000 real benign PE samples (Kaggle), teaching the model what a real "header data present, behavioral data absent" input actually looks like
PAC-X — balanced accuracy on real malware behavior49.8%80.6%Replaced a 10-item hand-picked keyword list with evidence-weighted scoring, mined and validated (proper train/val/test split) from 43,876 real Cuckoo Sandbox traces
In-distribution accuracy (this project's own test split)99.61%99.51%Negligible change — the original benchmark essentially held

What's disclosed, not hidden

The GNN fix has a real trade-off: it now leans toward "benign" when it can only see header data with no behavioral signal at all (a narrow input shape, not the typical real-file upload where PAC-X also has real content to check). Two attempts to fix this by adding real malicious samples in the same shape both caused training collapse — confirmed to be a genuine data limitation (no malware-family labels available in the source data), not a tuning problem, and not pursued further rather than force a broken fix.

Full evidence trail, all real measurements: data/kaggle_augmentation/validation_report.json (before/after model comparison), data/pacx_mining/mined_api_signals.json (PAC-X evidence weights + held-out test accuracy), data/ood_node_thresholds.json (the statistics behind step 4's out-of-distribution check), and data/retrain_repro/retrain_repro_report.json (the guardrail-failure reproduction referenced in step 6).
